# Platforms

What each operating system supports, how it is built, and how it is verified. Capabilities are discovered at runtime (`get_capture_capabilities`), so clients never have to assume a feature exists.

## Capability matrix

| Capability | Linux | Windows | macOS |
|------------|-------|---------|-------|
| Screen capture | XDG ScreenCast portal + PipeWire (monitor, window, virtual; picker only) | Windows.Graphics.Capture (monitors and windows by id from `list_capture_targets`; no picker yet) | ScreenCaptureKit (displays and windows by id from `list_capture_targets`; no picker yet; needs the screen-recording permission) |
| Audio input | PipeWire (format converted by PipeWire); each sink's monitor is an input too (desktop audio) | WASAPI through `cpal` (converted to 48 kHz stereo in the callback); each output's loopback is an input too (desktop audio) | CoreAudio through `cpal` (same conversion); each output's process tap is an input too (desktop audio, macOS 14.6 or newer) |
| Cameras (ADR 0019; `list_cameras`, `camera` sources) | PipeWire camera nodes (V4L2, libcamera, virtual cameras); YUV and MJPEG converted by `frame-decode`; tested with a virtual camera only | Media Foundation source reader (video capture devices by symbolic link); YUV and MJPEG converted to RGB32 by the system; Media Foundation loaded at run time (unavailable on N editions without the Media Feature Pack); CI has no camera, real cameras untested | AVFoundation capture session (cameras by `uniqueID`, built-in and external, virtual cameras too); YUV and MJPEG converted to BGRA by the system; needs camera access for the app that runs StreamForge; CI has no camera, real cameras untested |
| Monitor playback (ADR 0017) | PipeWire output stream (sinks and duplex devices) | WASAPI through `cpal` (48 kHz; Windows converts the rate) | CoreAudio through `cpal` (at the device's current rate, resampled in the callback) |
| Compositor, mixer, preview | yes | yes | yes |
| Recording (H.264 + AAC in Matroska) | FFmpeg (system packages) | FFmpeg (the package's own build; from source, any shared build) | FFmpeg (Homebrew) |
| Streaming (RTMP) | FFmpeg | FFmpeg | FFmpeg |
| Hardware encoders (`video_encoder: auto` tries them first, ADR 0011) | VAAPI (Intel, AMD; verified with an AMD RX 6800), NVENC | NVENC, Quick Sync, AMF | VideoToolbox |
| Desktop UI (egui) | yes | yes | yes |
| MCP server, JSON-lines engine, CLI | yes | yes | yes |

Notes:
- **Audio conversion (Windows, macOS):** WASAPI shared mode and CoreAudio deliver the device's own format.
  - The backend captures at the device's current rate (never switching it, which would affect other apps), preferring `f32` and stereo.
  - Unless that rate is 48 kHz, it resamples linearly, with the same quality note as the mixer's drift correction (ADR 0004).
  - Mono is duplicated to both channels; with more than two channels, the first two are used.
  - Each report warns about these conversions.
- **Monitor playback (Windows, macOS):** outputs are listed by `list_audio_outputs` with the host's device id and selected by it or by their display name, as inputs are.
  - Windows asks for the feed's 48 kHz, preferring `f32`, in the device's channel count (the only one cpal offers in shared mode); WASAPI's resampler converts the rate (cpal opens outputs with `AUTOCONVERTPCM`).
  - macOS plays at the device's current rate (never switching it), preferring `f32` and stereo. Unless that rate is 48 kHz, the callback resamples linearly, at the exact rate ratio, so no drift builds up there (the feed follows the device clock).
  - On both, stereo goes to the first two channels, silence to the others; a mono device gets their average.
  - The callback reads the feed into the device's buffer and does not lock, wait or allocate; formats other than `f32` go through a buffer allocated before the stream starts.
  - The system default output is resolved to its device when the monitor starts. cpal's default device follows the system default, which would move the monitor to the speakers when headphones are unplugged; as on Linux, the monitor stays on its device, and a device that goes away ends the monitor (`state: ended`, the reason names the output) within about 0.6 s, which closes the feed. A device that does not open and pull within 3 s is an error, as on Linux.
  - On macOS, a change of the device's rate also ends the monitor (cpal pauses the stream): another app or Audio MIDI Setup switching it, or Bluetooth headphones switching to their headset mode when their microphone is captured. Switch the monitor on again to play at the new rate. Captures from that device end the same way. Restarting on the same device by itself is left for the Windows and macOS work after the Linux release.
- **Desktop audio (Windows, macOS):** each output is listed by `list_audio_inputs` a second time, as `<output>.monitor` with `loopback_of` naming the output, as on Linux; so the feedback warning works there too. It captures what the output plays, from all apps, StreamForge's own monitor included, in the output's current format (on Windows its mix format), converted like any input. An output with more than two channels (5.1, 7.1, some gaming headsets) is not downmixed: only its first two channels are captured, so the center (dialog) and surrounds are missing, and the report warns. A downmix needs the channel layout, which cpal does not expose; it is left for the Windows and macOS work after the Linux release. (PipeWire downmixes on Linux.)
  - Windows uses WASAPI loopback. It delivers nothing while nothing plays, which would leave the input in warm-up and count underruns, so while it is captured StreamForge plays silence on that output (as OBS does).
  - macOS uses a process tap of all apps (cpal's loopback), which needs macOS 14.6 or newer and the permission to record system audio (System Settings → Privacy & Security → Screen & System Audio Recording). Without it, the tap delivers silence, which the capture report flags. An output that is an input too (a duplex device, as many USB interfaces are) has no monitor: cpal would open its input instead.
  - On macOS, cpal sets the output's physical format to the one it opens (the output's current rate and channels, `f32` where the device offers it), as it does when the monitor plays there; on a device in 24-bit integer mode that can switch its bit depth for every app.
- **macOS microphone access:** it needs permission for the app that runs StreamForge (System Settings → Privacy & Security → Microphone). Without it, CoreAudio delivers silence, which the capture report flags.
- **Device names:** audio inputs are selected by the host's device id (as listed by `list_audio_inputs`) or by their display name.
- **Choosing a capture target:** `get_capture_capabilities` says how (ADR 0010). With `picker` (Linux) the user picks in the system dialog. With `target_list` (Windows) `list_capture_targets` returns ids such as `monitor:\\.\DISPLAY1` or `window:4242:0x2a0b6` (process id and window handle), and screen commands take one as `capture_target_id`; the desktop UI shows that list.
- **macOS cameras:** listing needs no permission; capturing needs camera access for the app that runs StreamForge (the terminal, for the CLI and a desktop started from it; System Settings → Privacy & Security → Camera). The first start asks, which shows macOS's prompt; without an answer within 3 s, or with access denied, it fails `permission_denied` with that remedy, and `restart_source` opens the camera once it is allowed. `get_capture_capabilities` reports cameras unavailable while access is denied or restricted, without asking. A camera with only formats outside BGRA, ARGB, YUY2, UYVY, NV12, I420 and MJPEG is listed without modes and fails to start (`unsupported`). If the camera runs in another mode than the one chosen (another app may set it), the start warns and reports the mode it runs in. Two limits are not verified yet: macOS charges camera access to the app that launched StreamForge, and kills a process whose responsible app has no camera usage description when it asks (an MCP client, for example, unlike Terminal); and whether an unplugged camera is noticed, or a newly plugged one listed, in a process without a main run loop (the CLI, the engine process and the MCP server; the desktop runs one).
- **macOS screen capture:** needs macOS 14 or newer and the screen-recording permission for the app that runs StreamForge (System Settings → Privacy & Security → Screen & System Audio Recording). Without it, listing and capturing fail with `permission_denied` and that remedy. `get_capture_capabilities` does not ask, because asking can show the system prompt. Display ids are `display:<CGDirectDisplayID>`, window ids `window:<CGWindowID>`.
- **Windows screen capture:** needs Windows 10 version 1903 or newer. Windows draws a border around captured content (its privacy indicator). Frames arrive when the content changes; a static screen delivers few. Window ids are valid while the window exists; a closed window ends its capture with a warning.
- **Windows desktop app:** `streamforge-desktop.exe` is a window program (Windows subsystem), so no console window opens with it. Started from a console with nothing redirected, it attaches to that console while it reads its arguments, so `--version`, `--help` and startup errors print there (after the prompt has returned), and detaches before its window opens: Ctrl+C in that console then reaches the shell, not the app, which ends when its window closes. With redirected output (a pipe or a file) it keeps that output. The executable carries the app icon and version information (`build.rs`, through the Windows SDK's resource compiler).
- **Windows cameras:** Media Foundation converts native RGB, YUY2, UYVY, NV12, I420 and MJPEG to RGB32. Each native type of the chosen size and rate is tried, the chosen format first, then by rank. Every RGB32 output request includes a positive stride; if the negotiated type omits the stride, it is resolved from the subtype and width. Pixel rows are copied without touching 2D-buffer padding, including bottom-up buffers.
  - Modes are cached after a successful read. Camera privacy denial fails `list_cameras` with `permission_denied` and the hint to allow desktop apps in **Settings > Privacy & security > Camera**. Other failures to read a camera's modes (for example exclusive use) leave that camera listed without modes and retry on the next listing. Listing returns the devices and modes received within 10 s; unfinished cameras have no modes (or keep cached modes).
  - Start succeeds only after publishing a frame. A first-frame delivery error is returned after releasing the camera and its Media Foundation session. A start timeout sends Stop and waits up to another 4 s for teardown. Stop and Drop also wait up to 4 s and join once teardown is confirmed; a native driver call that stays blocked can outlast that bound and leave its worker closing in the background. Queued samples and the receiver are released before the session, and completion is sent afterward.
  - The stop report keeps the camera's native pixel format and rate, with the last observed frame size and a warning if the size changed while running. Real-camera behaviour still needs the manual Windows test; cross-compilation alone does not verify it.

## Building

| | Linux | Windows | macOS |
|-|-------|---------|-------|
| Rust | stable ≥ 1.95 | stable ≥ 1.95 (MSVC, with the Windows SDK for the desktop's resources); the C runtime is linked statically, which `.cargo/config.toml` sets (a `RUSTFLAGS` variable replaces that setting, so add `-C target-feature=+crt-static` to it) | stable ≥ 1.95 |
| FFmpeg | `libavcodec-dev libavformat-dev libavutil-dev libswscale-dev` (pkg-config) | a shared build with headers and import libraries; `FFMPEG_DIR` points to it, and its `bin` must be on `PATH` at runtime | `brew install ffmpeg pkgconf` |
| bindgen (FFmpeg bindings) | `libclang-dev` | LLVM (`LIBCLANG_PATH`) | Xcode command line tools |
| Capture | `libpipewire-0.3-dev` | — | Xcode 26 or newer (`screencapturekit` builds a Swift bridge against the macOS 26 SDK). Binaries need the rpath `/usr/lib/swift`, which `.cargo/config.toml` adds; a `RUSTFLAGS` variable replaces that setting, so add `-C link-arg=-Wl,-rpath,/usr/lib/swift` to it. |

CI uses the [BtbN FFmpeg builds](https://github.com/BtbN/FFmpeg-Builds) on Windows (`ffmpeg-n8.1-latest-win64-gpl-shared`). The archive is checked against the release's checksum file. Any FFmpeg 6.1 or newer with libx264 works. Binaries that link a GPL build fall under the GPL (ADR 0005).

The Windows package ships its own FFmpeg instead (ADR 0020): `packaging/windows/build-ffmpeg.sh` cross-compiles FFmpeg 8.1 with x264, NVENC, Quick Sync (libvpl), AMF and Schannel from the pinned archives in `packaging/ffmpeg/sources.txt` with mingw-w64 on Linux, as shared libraries with import libraries for the MSVC linker, and enables only what the engine uses. Its output works as `FFMPEG_DIR` for a local build too.

## Verification

CI (`.github/workflows/ci.yml`) builds and tests every push and pull request on `ubuntu-latest`, `windows-latest` and `macos-15-intel`:

| Test area | Linux | Windows | macOS |
|-----------|-------|---------|-------|
| Unit tests, command and protocol tests | CI | CI | CI |
| Recording: decode-and-check of real files | CI | CI | CI |
| Streaming to an in-process RTMP ingest, reconnect, give-up | CI | CI | CI |
| Engine, desktop-model and MCP acceptance tests | CI | CI | CI |
| Audio input | manual (dev machine); CI runners have no session | CI: the runner has no input, so the structured `not_found` path; live capture still needs a manual check. Monitors: listed per output; one is captured if the runner has an output | CI: the runner's devices if any, else the structured error; microphone permission cannot be granted on runners. Monitors: listed per output; capturing one needs the permission, so only on hardware |
| Hardware encoding | manual: VAAPI on the development machine (RX 6800, Mesa); NVENC untested. CI: no GPU; NVENC and VAAPI fail to open, and `auto` falls back to libx264 | CI: no GPU; NVENC, Quick Sync and AMF fail to open, fallback to libx264 | CI: VideoToolbox does not open on the VM, fallback to libx264 |
| Monitor playback | manual: live tests play into a null sink they create, and the engine end to end (`docs/capture-linux.md`) | CI: plays silence on the default output if the runner has one, else the structured error; unknown outputs and refused formats. Manual: a tone test (`--ignored`) on hardware | CI: as on Windows. Manual: the same tone test |
| Screen capture | manual (needs a human in the picker) | CI: lists sources, captures the runner's monitor (frames of its size), probes it, and records it from a scene through the engine process | CI: lists the runner's display, captures and probes it, and records it from a scene through the engine process (the runner image allows screen recording) |
| Cameras | manual: virtual PipeWire camera | CI: no camera, structured errors and unit tests; manual: default and smallest modes, advancing frame timestamps, stop/drop then reopen | CI: no camera; listing, access status, `not_found`, and the frame path with a synthetic sample buffer through the delegate; manual: as on Windows, plus a slower rate measured, and macOS's access prompt |

At the first complete CI run (ADR 0009), every test passed on Windows. On macOS, every test passed except a throughput floor, which on macOS is now only a guard against total failure: the macOS VM skips some compositor ticks at 1080p60, and those skips are counted.
